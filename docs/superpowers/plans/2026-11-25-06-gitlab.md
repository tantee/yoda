# GitLab (Plan 6 of 8) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Coding work flows through the department's self-hosted GitLab: projects link to GitLab repositories, every coding task gets a GitLab issue that the portal keeps up to date (its own marked section only), merge requests that close those issues move the work item forward (opened → implementation done, merged in every linked repo → code review done → QC), pipeline and comment activity shows in the portal, and an individual existing issue can be imported as a work item.

**Architecture:** New core module `gitlab/` with a small REST v4 client (fetch, bot token, retries), repository links per project and per work item, an issue-sync job that renders a deterministic snapshot section and only rewrites it when its hash changes, and a public webhook endpoint (secret-token verified, de-duplicated by event UUID) that records events and drives the workflow through the existing engine as the system actor. The portal gets a Repositories tab, a Code panel on work items, timeline labels, and an admin connection page. Tests use a local fake GitLab HTTP server — no real GitLab needed.

**Tech Stack:** as plans 1–5 (no new runtime dependencies; Node `fetch`).

**Spec:** `docs/superpowers/specs/2026-11-24-ai-work-portal-design.md` (§12 GitLab, §8 Dev step, §17 calls 3 and 6, §3 requesters never see GitLab links). Follow-ups: `docs/superpowers/plans/2026-11-25-05-discussions-followups.md`.

**Not in this plan:** runners pushing branches and opening MRs (plan 7), GitHub support, bulk import of existing issues, CI configuration.

## Defaults chosen in this plan (owner can override)

1. **Merge means reviewed.** When a merge request that closes a portal-created issue is merged in GitLab, the portal accepts the `review-code` task as the system (reason `merged_in_gitlab`), because the review happens in GitLab. With several repos, this happens only when every linked repo's MR is merged.
2. **MR opened means implemented.** When an MR closing the issue is opened, the `implement` task is accepted with the MR links as its result (whether a person or AI owned it).
3. **Which repos a work item touches:** all repos linked to the project by default; PMs can change the list until the Dev step starts.
4. **Issue language:** the issue body uses the work item's own text (Thai or English); the portal's fixed headings are bilingual ("ข้อกำหนด / Requirements").
5. **Issue comments from developers** become timeline events and `draft` knowledge notes on the work item.

## Global Constraints

- The portal owns only the text between `<!-- yoda:begin -->` and `<!-- yoda:end -->` in an issue body; everything outside is left untouched. The portal never edits labels, assignees or milestones.
- Content changes to the owned section are pushed only when the rendered section's hash changes; each push after the first adds an issue comment summarizing what changed.
- Webhooks are verified with `X-Gitlab-Token` (constant-time compare) and de-duplicated by `X-Gitlab-Event-UUID`; unknown projects/MRs are acknowledged (200) and ignored.
- Requesters never see GitLab links, issue numbers, MR states or pipeline details anywhere (task pages, requests, chat, notifications).
- The bot token comes only from env (`GITLAB_TOKEN`); never logged, never returned by any API, never stored in the DB.
- Without `GITLAB_URL`/`GITLAB_TOKEN` configured, the portal works as before; GitLab features show "not connected".
- Workflow effects from GitLab go through the existing engine (`runWork` with actor `{ id: null, kind: 'system' }`), respect open discussions (plan 5) and auto-assign guard rails (plan 4).
- Lock order unchanged: project → work item → task → proposal/discussion; work item rows `FOR NO KEY UPDATE`.
- Thai default UI, all strings via i18n, th/en parity. Repo is public: no secrets.

## Review Focus

1. **A forged or replayed webhook** (wrong token, reused event UUID, MR in an unlinked project, MR that mentions an issue the portal didn't create) → no workflow effect. Tests in Task 5.
2. **A merge in one repo of a two-repo work item** → no review acceptance until the second merges; a closed-without-merge MR doesn't count. Test in Task 6.
3. **GitLab down or slow** during issue sync → job retries with backoff, the work item isn't blocked, the portal shows "sync pending"; the token never appears in logs or errors. Test in Task 4.
4. **A developer edits the issue outside the portal's markers** (or deletes the markers) → the portal preserves their text; if markers are gone it re-appends its section at the end instead of overwriting. Test in Task 4.
5. **Requester probing** task/request/chat responses for GitLab URLs or MR states → none present. Test in Task 7.

### Task 4: Issue sync

**Files:**
- Create: `apps/core/src/gitlab/issue-section.ts`, `apps/core/src/gitlab/sync.ts`
- Modify: job registration (`gitlab-issue-sync`), `apps/core/src/work/tasks.ts` or `engine.ts` (enqueue when a `code-change` task is created), `apps/core/src/knowledge/service.ts` hooks (enqueue re-sync when a confirmed document/decision on the item changes), `apps/core/src/discussions/service.ts` (on decide)
- Test: `apps/core/test/gitlab-sync.test.ts`, `apps/core/test/issue-section.test.ts`

**Interfaces:**
- `renderIssueSection(input: { workItem; projectName; portalUrl; requirements: string | null; design: string | null; decisions: { question: string; decision: string }[]; testCases: string | null; siblings: { path: string; iid: number | null; url: string | null }[]; feedback: string | null }): string` — deterministic Markdown between the markers: title line, link back to the portal work item (`${portalUrl}/work-items/<id>`), sections with bilingual fixed headings (ข้อกำหนด / Requirements, การออกแบบ / Design, การตัดสินใจ / Decisions, กรณีทดสอบ / Test cases, งานที่เกี่ยวข้อง / Related issues), each document clipped to 6 000 chars with a "… (ดูต่อในพอร์ทัล / continued in the portal)" link; closing note asking MRs to include `Closes #<iid>`. Uses confirmed documents only (requirements = approved BA output, design = approved SA output), decided discussions, QC draft-tests result if accepted. No requester names.
- `mergeSection(body: string, section: string): string` — replaces the text between markers; if markers are missing, appends the section at the end separated by a blank line.
- `sectionHash(section: string): string` (sha256 hex).
- Job `gitlab-issue-sync` `{ id: workItemId }`: for each `work_item_repos` row of the item: if no issue yet → `createIssue` (title = work item title, description = section) and store iid/url; else `getIssue` → `mergeSection` → `updateIssue` only if the hash changed, then `addIssueNote` with a short "updated sections: …" note (not on the first creation). Records `gitlab.issue_synced` (or `gitlab.issue_sync_failed` with a short code after the final attempt), sets status; GitLab errors retry (pg-boss retry); `not_found` on an existing issue → status failed `issue_missing` (no recreate). No-op when GitLab isn't configured (status stays pending).
- Enqueue points (after commit): a `code-change` task created for the item (Dev step starts); a confirmed document/decision entry created or updated on the item while it has issues; a discussion decided on the item; a new `implement` attempt with feedback (feedback goes into the section's "Changes requested" line).

**Interfaces:**
- Job `gitlab-mr-effect` `{ id }` (runs as `{ id: null, kind: 'system' }`, locks the work item then tasks):
  - **MR opened (or merged) and linked:** the item's active `implement` task (template capability `code-change`) in the current step → accepted with result text listing the MR links (`ai`/`human` executor alike, even unassigned), event reason `mr_opened_in_gitlab`; if no active implement task, nothing.
  - **All repos merged:** when every `work_item_repos` repo of the item has at least one linked MR in state `merged`, the active `review-code` (template task of type `review` depending on the code-change task) → accepted with decision `approve`, result text "Merged in GitLab: …", reason `merged_in_gitlab`; then `progressWorkItem` (discussions and guard rails apply as usual).
  - **MR closed without merge:** notify the project PMs and the implement assignee (dedupe `mr-closed:<mrId>`); no task change.
  - Idempotent: re-running for the same MR state changes nothing.
- The review task's PM/assignee can still approve or request changes in the portal before the merge; a later merge then does nothing if the task is no longer active.

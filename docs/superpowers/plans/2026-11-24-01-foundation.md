# Foundation (Plan 1 of 8) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A running monorepo where staff and requesters log in through Keycloak, the core service knows who they are (staff/requester/admin), admins manage projects and members, and the portal shows the correct role-based shell.

**Architecture:** pnpm monorepo with `apps/core` (Fastify REST API, Drizzle on Postgres), `apps/portal` (Nuxt 4 SPA + Vuetify, keycloak-js), and `packages/shared` (zod schemas and types used by both). Core verifies Keycloak access tokens itself (JWKS); the portal proxies `/api/**` to core. A dev `docker-compose.yml` provides Postgres (pgvector), MinIO and Keycloak with a seeded realm.

**Tech Stack:** Node 22+ (local machine has 22; images use node:22-alpine), pnpm 10, TypeScript (strict), Fastify 5, Drizzle ORM + drizzle-kit, `postgres` driver, zod, jose, Vitest, Nuxt 4, Vuetify 3 (`vuetify-nuxt-module`), keycloak-js, Docker Compose, Keycloak 26, `pgvector/pgvector:pg17`, MinIO.

**Spec:** `docs/superpowers/specs/2026-11-24-ai-work-portal-design.md`

### Roadmap (each is its own plan, written when the previous one is done)

1. **Foundation** (this plan): monorepo, auth, people, projects, portal shell.
2. **Work model & To-do**: WorkItem, Task state machine, Event log, workflow templates (seeded "Software change", "Bug fix"), To-do screen, SSE realtime.
3. **Knowledge & AI gateway**: knowledge entries with draft/confirmed trust, versioning, pgvector + pg_trgm search, attachments in MinIO, context packs, provider-neutral AI gateway with cost log and budgets.
4. **Chat & Secretary**: conversations/messages with attachments, event-driven secretary with tools, autonomy levels, anti-nag rules, requester intake view.
5. **Discussions**: AI briefs, agenda view, decisions flowing to work items and knowledge.
6. **GitLab**: issue per coding task (owned section), webhooks → events, multi-repo work items.
7. **MCP server & runners**: runner protocol tools, leases, server runner (Agent SDK), dev-machine runner (on-demand + unattended).
8. **Status & release**: dashboards, weekly AI summaries, digests, production deployment.

## Global Constraints

- Single TypeScript monorepo, pnpm workspaces: `apps/portal`, `apps/core`, `apps/runner` (plan 7), `packages/shared`.
- Authentication is hospital **Keycloak** via OIDC for both IT staff and requesters.
- Staff vs requester: membership of a configurable Keycloak group (`STAFF_GROUP`), overridable per person by Admin (`staffOverride`). Everyone else is a Requester.
- Skills/areas tags and per-project roles live in the portal DB, not Keycloak.
- Project roles: `PM`, `BA`, `SA`, `DEV`, `QC`. A person may hold several roles per project. System role: Admin.
- Requesters never see projects, other people, or internal data (in this plan: every staff/admin route returns 403 for them).
- UI is bilingual Thai/English, Thai default (set up i18n now; all strings via i18n keys).
- Postgres extensions `vector` and `pg_trgm` enabled from the first migration.
- Scale: ~30 staff, ~10 projects — single instance of each app; no caching layer.
- No secrets in the repo; config via environment validated with zod at startup. The repo may be pushed to GitHub, so treat it as public:
  - `.gitignore` covers `.env`, `.env.*` (except `.env.example`), `*.pem`, `*.key`, `secrets/`, `.claude/settings.local.json`.
  - `.env.example` holds placeholders only; the only literal credentials allowed in the repo are the dev-only Keycloak test users (password `dev`) and dev MinIO/Postgres defaults inside `docker-compose.yml`, each marked `# DEV ONLY`.
  - A gitleaks pre-commit hook (via `lefthook`) and a gitleaks CI job block commits/pipelines containing secrets.
  - Production secrets come only from the deploy environment (CI variables / server env), never from committed files.

## Review Focus

1. **Expired, wrong-issuer, or wrong-client tokens** → 401, never a created person. Test in Task 4.
2. **Requester profiles missing email or names** (external staff accounts are often incomplete) → person still created with `displayName` falling back to `username`. Test in Task 4.
3. **Staff status changes in Keycloak** (removed from `STAFF_GROUP`) → loses staff access on the next request; staff status is computed per request, never frozen at first login. Test in Task 4.
4. **Thai names and text** round-trip intact through API and DB. Test in Task 4 (Thai display name) and Task 5 (Thai project name).
5. **Two first requests from the same new user at once** → exactly one person row (upsert on `keycloak_sub`). Test in Task 4.

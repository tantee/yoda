# MCP Server & Runners (Plan 7 of 8) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** AI tasks that need a repository (`code-change`, `analyze-repo`, `run-tests`) are worked by runners: a server runner or a developer's own machine claims a task through core's MCP server, gets the context pack, works in an isolated git worktree with Claude Code or Codex, pushes a `yoda/…` branch, has core open the merge request, and submits the result. A runner that needs a person asks through a discussion and moves on. Developers can also connect Claude Code to the same MCP server and work a task by hand with full context.

**Architecture:** Core gets a `runners/` module: runner records with hashed tokens tied to a person, agent runs with a lease and heartbeat, safeguards checked on every claim (pauses, working hours, concurrency, account policy, no-AI, budget, project visibility), and an MCP server (`/mcp`, official MCP TypeScript SDK, Streamable HTTP, stateless) exposing the runner protocol. Core keeps the GitLab bot token and opens merge requests itself, so runners need only git push access. A new `apps/runner` Node CLI drives the loop: it talks to core only through MCP, creates a git worktree per task, launches the agent CLI headless with core's MCP server attached, and guards against pushing to the default branch.

**Tech Stack:** as plans 1–6, plus `@modelcontextprotocol/sdk` (core server and runner client). The runner launches the `claude` CLI (`-p`, `--mcp-config`, `--strict-mcp-config`, `--output-format json`, `--permission-mode`) or the `codex exec` CLI as child processes; it does not embed a model SDK.

**Spec:** `docs/superpowers/specs/2026-11-24-ai-work-portal-design.md` (§7 AgentRun, §10.4 context packs, §11.1–11.3 runner protocol and types, §14 runner tokens, §17 call 4 dev-machine modes and safeguards). Follow-ups: `docs/superpowers/plans/2026-11-24-02-work-model-todo-followups.md`, `2026-11-24-03-knowledge-ai-followups.md`, `2026-11-24-04-secretary-followups.md`, `2026-11-25-05-discussions-followups.md`.

**Not in this plan:** status dashboards and release packaging (plan 8), runners for GitHub, sandboxing beyond the container boundary (network egress rules are deployment work), auto-retrying a run on a different runner type.

## Defaults chosen in this plan (owner can override)

1. **Personal subscriptions are not used unattended.** A runner whose account type is `personal-subscription` can work tasks only on demand (`yoda-runner work <id>`). Unattended claims are refused unless an admin turns on "Allow personal subscriptions unattended" after checking the provider's current terms (spec §17.4). The default is off.
2. **Who owns a runner.** Every runner acts for one staff person, the owner. Its knowledge notes, discussions and results are attributed to "AI on behalf of <owner>". Staff create runners for their own machines. Admins create server runners and choose the staff owner.
3. **Runner cost.** Core can't meter a runner's model usage, so a runner reports usage with its result (model, tokens, cost when known). Reported cost counts toward the project's monthly AI budget. Claims are refused when the project's budget is used up or the project is no-AI.
4. **Merge requests come from core.** The runner pushes `yoda/<8hex>-<slug>` and asks core to open the MR, with `Closes #<iid>` added by core. MRs target the repo's default branch. Pushing to the default branch is refused by the runner, and core refuses MRs whose source is the default branch.
5. **Failure budget.** After 3 failed or expired runs on the same task attempt, the task returns to people (the existing "AI couldn't finish" path, `failAiTask`).
6. **Lease.** 10 minutes, extended by heartbeats every 60 s. A missed lease returns the task to the queue within a minute.

## Global Constraints

- Runner tokens are 32 random bytes, base64url, prefixed `yoda_rt_`. They are shown once at creation and only the SHA-256 hash is stored. Tokens are never logged or returned again, and a revoked runner's token stops working immediately.
- Runners act as their owner. Searches and reads use the owner's visibility, writes go through the owner's `Me` and are never `null`, and runners never use `SYSTEM_ME`. Events use actor `{ id: owner, kind: 'ai' }`, which records `onBehalfOf`.
- Only `executor = 'ai'`, open, unassigned tasks whose template capability is in the runner's capabilities are offered to unattended runners. `draft-text` is never offered, because core drafts it. No-AI projects and parked tasks are never offered.
- One active run per task (unique partial index). A claim is atomic: two runners claiming the same task get one success and one `invalid_state`.
- Requesters never see runners, runs, branches or progress notes.
- No GitLab or model HTTP call happens inside a DB transaction. Jobs are sent after commit. Lock order is unchanged: project → work item → task → proposal/discussion.
- Repo is public: no secrets. Dev-only literals are marked `# DEV ONLY`. Thai is the default UI, with th/en parity.

## Review Focus

1. **A laptop that sleeps mid-task:** no heartbeat, so the lease expires, the task goes back to the queue and the run is marked `expired`. A later heartbeat or submit from the stale run is refused with `invalid_state`. Test in Task 3.
2. **Two runners racing for one task:** one wins and the other gets 409. Tests in Task 3.
3. **A revoked or paused runner, the global pause, outside working hours, at max concurrency, or a personal subscription unattended:** the claim is refused with a clear code, and work already claimed can still be submitted. Tests in Task 3.
4. **A runner token used to reach staff REST routes, or a Keycloak token used on `/mcp`:** both refused, with no crossover. Tests in Tasks 2 and 6.
5. **An agent that tries to push to `main` or open an MR from the default branch:** refused by the runner before the push and by core on the MR call. Tests in Tasks 5 and 7.

### Task 3: Claims, leases and safeguards

**Files:**
- Create: `apps/core/src/runners/claims.ts`, `apps/core/src/runners/safeguards.ts`; Modify: `apps/core/src/jobs/queue.ts` + `handlers.ts` (schedule `runner-lease-sweep` every minute), `apps/core/src/work/queries.ts` (task view: `run` summary for staff)
- Test: `apps/core/test/runners-claims.test.ts`

**Interfaces:**
- `RunnerCtx = { runner: RunnerRow, owner: Me }`.
- `listAvailableTasks(deps, rc, input: ListTasksInput): Promise<AvailableTask[]>`.
  - Each `AvailableTask` is `{ taskId, title, workItemId, workItemTitle, projectName, capability, stepKey, priority, createdAt }`.
  - The list is ordered by work item priority (urgent first), then oldest, limited to 20.
  - Filters:
    - The task is `executor='ai'`, `state='open'`, unassigned, current step, not superseded, and `parked_discussion_id` is null or its discussion is decided.
    - The capability is in the runner's capabilities ∩ `input.capabilities`, and isn't draft-text.
    - The project is visible to the owner and isn't no-AI.
- `claimTask(deps, rc, taskId): Promise<{ run: AgentRun }>` runs in `runWork` as `{ id: owner, kind: 'ai' }`.
  - Lock order: project share → item → task `FOR UPDATE`.
  - It checks `checkSafeguards(tx, rc, { unattended })` and returns the first failure as 409 `invalid_state` with `reason` ∈ `runner_paused | all_runners_paused | outside_hours | at_capacity | personal_unattended_not_allowed | no_ai | budget_exceeded`.
  - Task eligibility is the same as the list, except it also allows a task assigned to the owner (any executor) for on-demand use.
  - A task that already has a running run → 409 `invalid_state` (the unique index is the backstop).
  - It sets the task `in_progress`, inserts the run with `lease_expires_at = now + RUNNER_LEASE_SECONDS` and records `run.claimed`.
  - `unattended` is true when `runner.mode === 'unattended'` and the task is unassigned; claiming the owner's own assigned task counts as on-demand.
- `heartbeat(deps, rc, runId)` extends the lease. `requireLiveRun(tx, rc, runId)` → run row or 409 `invalid_state` (`run_not_active`) when the run isn't `running`, belongs to another runner, or its lease has passed.
- `releaseRun(deps, rc, { runId, reason, failed })`: the run becomes `failed` or `released`, the task goes back to `open` (AI tasks), and `run.failed`/`run.released` is recorded. On the 3rd failed or expired run for the same task row, it calls `failAiTask(ctx, taskId, 'runner_failed')`.
- `expireLeases(deps)` is the job:
  - Running runs past their lease become `expired`.
  - Their tasks go back to `open`, except tasks assigned to a person, which stay with them.
  - It records `run.expired` and applies the 3-strike rule.
- `checkSafeguards` order:
  1. Revoked — but authentication already blocks a revoked runner.
  2. `runner_settings.paused`.
  3. `runner.paused`.
  4. Working hours, when set and unattended, in Asia/Bangkok.
  5. Active runs ≥ `max_concurrent`.
  6. Personal subscription + unattended + not allowed.
  7. The project is no-AI.
  8. The project's month usage ≥ budget (`monthUsage` from the gateway module).
- Work item task view: for staff, each task gets `run: { state, runnerName, heartbeatAt, branch } | null` for the latest run. The `waitingForAi` logic still works.

**Interfaces:**
- `GitLabClient.createMergeRequest(projectId: number, input: { sourceBranch, targetBranch, title, description, removeSourceBranch: true }): Promise<{ iid: number, webUrl: string, state: string }>`.   - It upserts the `merge_requests` row linked to the work item (state `opened`), records `gitlab.mr_requested`, and stores the branch on the run.
  - The existing MR webhook and effects then accept the implement task as in plan 6. `submitResult` stays idempotent with that.

**Interfaces:**
- `workTask(deps, taskId | { runId, alreadyClaimed })`:
  1. Claim the task.
  2. Start a heartbeat every 60 s.
  3. Get the context pack.
  4. Prepare a workspace per repo in `code.repos`. The first version supports one repo per run: with several repos, work the first repo that has no merged MR, and say so in the summary.
  5. Run the executor.
  6. If `needsHuman` or the run was parked (the agent called `ask_human`), stop: no push, the run is already `parked`.
  7. If `ok` and there are new commits, push the branch and call `open_merge_request`.
  8. Call `submit_result` with the summary, MR links and usage.
  9. If it failed, call `release_task` with `failed: true` and the error.
  10. Always clean up the worktree and stop the heartbeat.
  - For non-code capabilities (`analyze-repo`, `run-tests`), skip push and MR and submit the summary.
- `startLoop(deps, { once?: boolean })`:
  - Each poll it calls `list_available_tasks`, then claims and works up to the runner's `maxConcurrent` in parallel.
  - A claim refusal with `outside_hours`/`*paused`/`at_capacity` → wait for the next poll. `personal_unattended_not_allowed` → log once and exit with code 2.
  - SIGINT/SIGTERM → stop polling, release running work with `failed: false` (reason `runner_stopped`), and exit.

  - `yoda-runner work <taskId>` (on demand)
  - `yoda-runner start` (unattended)
  - `yoda-runner mcp-config` prints the Claude Code MCP config JSON for interactive use, with the token read from config at run time and printed only when `--with-token` is passed.
  - `yoda-runner config show` (masked)

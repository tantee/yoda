# Chat & Secretary (Plan 4 of 8) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every staff member and requester can chat with an AI secretary that answers from project knowledge, turns requests into work items (with confirmation), and keeps people informed; requesters get their own "My requests" and "Things I need to answer" views; in `propose` projects the PM confirms step advances and priority changes from one confirmation list; and people get a de-duplicated notification feed instead of a flood.

**Architecture:** New core modules `chat/` (conversations, messages, read state), `proposals/` (pending PM decisions executed on accept), `notifications/`, and `secretary/` (tool-calling AI over the plan 3 gateway, run as pg-boss jobs per message and per event, acting with the permissions of the person it serves). The workflow engine gains a requester on work items, a `REQUESTER` template role, a step-advance gate in `propose` mode, a daily per-person task cap, and role-removal unassignment. The live stream gains conversation events and opens (filtered) to requesters. Portal gets a real Chat page, notification bell, proposals in the To-do confirmations, and the requester pages.

**Tech Stack:** as plans 1–3 (AI SDK v7 tool calling via the existing gateway, pg-boss, Drizzle, Fastify, Nuxt + Vuetify + i18n).

**Spec:** `docs/superpowers/specs/2026-11-24-ai-work-portal-design.md` (§3 requester, §9 secretary, §13 Chat/Requester view). Follow-ups: `docs/superpowers/plans/2026-11-24-02-work-model-todo-followups.md`, `docs/superpowers/plans/2026-11-24-03-knowledge-ai-followups.md`.

**Not in this plan:** discussions and `raise_discussion` (plan 5), GitLab-triggered reactions (plan 6), MCP/runners (plan 7), status dashboards and email/LINE notifications (plan 8), token-by-token streaming of secretary replies (replies arrive as whole messages with a "typing" indicator).

**Answers:** Q1 → (b) department-wide budget. Q2 → admin only. Storage → RustFS. The owner also accepted `propose` as the default for existing projects and To-do as the staff home page. An "auto when there's no doubt" mode is being clarified — nothing new is built for it in this plan.

### Original questions

**Q1. How are secretary AI calls budgeted when there is no project?** Chat in a personal thread or a requester's intake thread isn't tied to a project, and today the gateway skips budget and "do not send to AI" checks for `projectId: null`.
- (a) **Per project only:** the secretary must resolve a project before calling AI with project content; project-less calls (small talk, "what's on my plate") are charged to nobody but still logged.
- (b) **Department budget:** a new department-wide monthly AI budget (admin-set) covers all project-less calls; same 80%/100% rules as projects.
- (c) **Charge the person's projects proportionally** or another scheme.
- Proposal in this plan if the owner picks (b): `department_settings.ai_budget_usd`, `ai_calls.project_id null` rows count toward it.
- **Blocks:** Task 7 (gateway chat billing), Task 8 (secretary chat), Task 9 (event reactions that call AI).

**Q2. Who may edit a project's "do not send to AI" flag and its AI budget — admin only (spec §14) or the project PM too (current code)?**
- **Blocks:** Task 10 only (permission alignment, tests, portal controls). No other task depends on it.

Tasks 1–6 do not depend on Q1 or Q2 and may proceed once this plan is approved.

## Global Constraints

- The secretary acts **on behalf of the person it is talking to**: every tool call is permission-checked as that person; events it causes record actor kind `ai` with payload `onBehalfOf: <personId>`.
- Always human: the secretary never approves, rejects or submits tasks, never confirms its own proposals, never changes project settings or memberships.
- Creating work items from chat always goes through a confirmation (an action card the person confirms).
- `propose` autonomy (default): step advances and secretary-suggested priority changes become proposals the PM confirms; `auto-assign`: they apply directly. Task assignment proposals keep the plan 2 mechanism (`task.proposed`).
- Anti-nag: notifications are de-duplicated by key; no person receives more than `DAILY_TASK_CAP` (default **8**) automatic task assignments per Bangkok calendar day — beyond that, the task is left for the PM; the secretary never creates a task without a stated expected result.
- Requesters see only their own requests, their own conversations, and tasks assigned to them with role `REQUESTER`; never internal discussions, other projects, knowledge beyond their request's attachments, or GitLab links.
- "Do not send to AI" rules from plan 3 apply to every secretary prompt (context packs, search with `forAi: true`, attachments).
- Thai default UI, every string via i18n, th/en parity. Repo is public: no secrets.
- Follow plan 1–3 patterns (`runWork` with actor kinds, jobs after commit, `HttpError` helpers, test helpers, mock AI models, `TEST_STORAGE=memory` in CI).

## Review Focus

1. **A requester probing ids** (other people's requests, conversations, tasks, attachments, the live stream) → 403/404 and no leaked events. Tests in Tasks 3, 4.
2. **The secretary asked to do something the person isn't allowed to** (create a work item in a project they don't belong to, read another project's knowledge) → the tool refuses and the reply says so; nothing is created. Test in Task 8.
3. **Two PMs accepting the same proposal at once, or accepting a proposal whose situation changed** (step already advanced, work item cancelled) → exactly one applies; the other gets 409 and the proposal shows its final state. Test in Task 5.
4. **A burst of assignments to one person** (e.g. 10 bug fixes created at once) → that person gets at most `DAILY_TASK_CAP` automatic assignments that day; the rest wait in the PM's confirmations; notifications are de-duplicated. Test in Task 6.
5. **Secretary failure mid-conversation** (provider down, budget stop, malformed tool arguments) → the person sees a short system message explaining the secretary couldn't answer; no half-applied tool effects. Test in Task 8.
